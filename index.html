#1. Executive Summary

This plan upgrades the kwg-nonprod EKS cluster from Kubernetes 1.34 to 1.36 via two in-place minor-version hops. Each hop follows the same repeatable sequence:

Control Plane → Core Add-ons → Data Plane (Bottlerocket MNGs) → Validate → Soak

The non-prod upgrade serves a dual purpose:

  1. Deliver a supported, patched non-prod platform.
  2. Act as the rehearsal and evidence-gathering run for the subsequent production upgrade. Every deviation, failure and fix must be captured in the Learnings Log (Section 12) and folded back into the production runbook.

Critical architectural constraint: An EKS control plane cannot be downgraded. Once update-cluster-version succeeds, rollback is only possible by rolling forward (fix) or by rebuilding a cluster at the prior version and re-pointing CloudFront. This asymmetry drives the entire gate design in this plan.

#3.2 Where the Upgrade Actually Hurts

The control-plane upgrade is largely non-disruptive. Essentially all risk to the traffic path lives in the data-plane node rotation, where every pod on the cluster is evicted and rescheduled.

Path element Upgrade impact Primary mitigation
CloudFront origin (NLB DNS) If the nginx Service is deleted/recreated (manual helm upgrade with different values, helm uninstall, resource rename, chart bump) a new NLB with a new DNS name is created. CloudFront origin silently points at a dead endpoint → full outage. Argo CD cannot cause this — but equally cannot prevent or repair it, because nginx is outside GitOps. Manual change freeze on the nginx release for the whole window (human control, not a sync window). Record NLB ARN + DNS as a gate artifact; verify byte-identical pre vs post. Never run helm upgrade on nginx during the window.
NLB targets Node replacement de-registers old targets and registers new ones. Default deregistration delay (300s) plus health-check ramp can create a draining window. Rolling, AZ-by-AZ node rotation with maxUnavailable=1. nginx preStop sleep ≥ target deregistration delay. Verify target group health before each subsequent node.
nginx layer nginx pods are evicted during node rotation. If nginx has 1 replica or no PDB, ingress drops entirely. No controller will self-heal it — recovery is manual. nginx replicas ≥ 3, spread across AZs via topologySpreadConstraints, PDB maxUnavailable: 1. Applied via a recorded values file (Section 5.7), as a separate change before the window.
45 microservice pods Mass eviction + reschedule. Scheduling failures if resource requests exceed surge capacity. Singletons cause per-service blips. Pre-flight PDB + replica audit. HPA minReplicas ≥ 2 for user-facing services. Capacity headroom check.
In-cluster Prometheus scraper Scraper pod eviction = metrics gap, which blinds you precisely when you need observability most. If it is a single-replica StatefulSet with a PVC, it must reschedule into the same AZ. Treat scraper as a Tier-0 workload. Verify AZ/PVC affinity. Accept and annotate the gap; do not let alerting flap. Silence AMG alerts for the window.
Log forwarder DaemonSet → EC2 ELK DaemonSet pods terminate with the node. In-flight buffers can be lost; new node pods re-tail from position 0 → possible duplicate or missing logs. Confirm forwarder image supports target K8s version. Accept duplicates in non-prod; validate ELK ingest continuity post-hop.
Argo CD itself Argo CD runs in the cluster being upgraded. Its own pods get evicted; it may attempt to self-heal workloads mid-rotation. Upgrade Argo CD before the cluster. Run HA mode or accept controlled downtime. Apply a Sync Window to freeze reconciliation during the window.
Warning

The ingress tier is the least protected part of this platform. The 45 microservices are declarative, reconciled and rebuildable from Git. nginx — the single component every one of them depends on for inbound traffic — is none of those things. It is a hand-run helm upgrade whose only record is a Secret inside the very cluster being upgraded.

This inverts the usual intuition: the layer with the highest blast radius has the weakest recovery story. Sections 5.7 and 6 therefore treat capturing and externalising the nginx release state as blocking pre-work, not documentation housekeeping.

kubectl get apiservices — any aggregated API service (metrics-server, custom metrics adapters, cert-manager webhooks) that is False (Unavailable) before the upgrade will produce confusing failures after. Fix these first.

#5.2 Deprecated / Removed API Scan — mandatory, blocking

Critical

VERIFICATION GATE — do not take this plan's word for 1.35/1.36 specifics. At execution time, the responsible engineer must read and attach to the change ticket:

  • The official Kubernetes Deprecated API Migration Guide for 1.35 and 1.36.
  • The Kubernetes CHANGELOG (CHANGELOG-1.35.md, CHANGELOG-1.36.md) — "Urgent Upgrade Notes" and "Removed/Deprecated" sections.
  • The Amazon EKS Kubernetes versions release-notes page for 1.35 and 1.36.

This plan deliberately does not enumerate specific 1.35/1.36 removals, because stating them without verification is exactly how upgrades break. The scanning below is the safety net, not a substitute for reading the notes.

Run all three, independently:

# 1) AWS EKS Cluster Insights — AWS's own upgrade-readiness checks
aws eks list-insights --cluster-name $CLUSTER --region $REGION
aws eks list-insights --cluster-name $CLUSTER --region $REGION \
    --filter '{"categories":["UPGRADE_READINESS"]}' \
    --query 'insights[].{id:id,name:name,status:insightStatus.status}' --output table

# Drill into every insight that is not PASSING
aws eks describe-insight --cluster-name $CLUSTER --id <INSIGHT_ID> --region $REGION

# 2) Pluto — scan the *Git repo* (source of truth), not just the live cluster
pluto detect-files -d ./gitops-repo --target-versions k8s=v1.36.0 -o wide
pluto detect-helm --target-versions k8s=v1.36.0 -o wide

# 3) Live-cluster deprecation warnings
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis
Tip

apiserver_requested_deprecated_apis is the highest-signal check available — it reports deprecated APIs that are actually being called right now, including by controllers whose manifests you don't own. Chase every non-zero series to its User-Agent.

Exit criterion: zero unresolved UPGRADE_READINESS insights; zero Pluto findings at target 1.36; zero deprecated-API call series attributable to in-scope workloads.

#5.4 Workload Resilience Audit (the 45 microservices)

# Replica counts — find singletons
kubectl get deploy -A -o custom-columns=\
'NS:.metadata.namespace,NAME:.metadata.name,REPLICAS:.spec.replicas,AVAIL:.status.availableReplicas'

# PDBs — the #1 cause of stalled node-group upgrades
kubectl get pdb -A -o custom-columns=\
'NS:.metadata.namespace,NAME:.metadata.name,MIN:.spec.minAvailable,MAX:.spec.maxUnavailable,ALLOWED:.status.disruptionsAllowed'

# Any PDB with ALLOWED=0 WILL stall the drain:
kubectl get pdb -A -o json | jq -r '.items[]
  | select(.status.disruptionsAllowed==0)
  | "BLOCKER: \(.metadata.namespace)/\(.metadata.name)"'

# HPA minReplicas
kubectl get hpa -A -o custom-columns=\
'NS:.metadata.namespace,NAME:.metadata.name,MIN:.spec.minReplicas,MAX:.spec.maxReplicas,TARGETS:.status.currentMetrics'

# PVCs and their AZ pinning (R-12)
kubectl get pv -o custom-columns=\
'NAME:.metadata.name,CLAIM:.spec.claimRef.name,AZ:.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]'

Remediation standard (apply via Git / Argo CD for the 45 microservices; via a recorded helm upgrade -f nginx-values.yaml for nginx — see §5.7 — well before the window):

Control Standard for user-facing services
replicas / HPA minReplicas ≥ 2 (≥ 3 for nginx)
PodDisruptionBudget maxUnavailable: 1 (preferred over minAvailable — it scales safely)
topologySpreadConstraints Spread across topology.kubernetes.io/zone
Readiness probe Present and accurate
preStop hook sleep ≥ NLB deregistration delay (for nginx)
terminationGracePeriodSeconds > preStop sleep + app drain time
Resource requests Set — required for the scheduler to place pods during surge

#5.5 Capacity & Networking Pre-checks

# Free IPs per subnet — node surge needs them, and so does VPC CNI
aws ec2 describe-subnets --region $REGION \
  --subnet-ids $(aws eks describe-cluster --name $CLUSTER --region $REGION \
                 --query 'cluster.resourcesVpcConfig.subnetIds[]' --output text) \
  --query 'Subnets[].{AZ:AvailabilityZone,Subnet:SubnetId,Free:AvailableIpAddressCount}' \
  --output table
  • Control plane requirement: EKS needs at least 5 free IP addresses in the cluster subnets to perform the version upgrade. Treat < 10 free as a blocker.
  • Data plane requirement: surge capacity = maxUnavailable (or surge count) × node ENI/IP consumption, per AZ.
  • Confirm the cluster security group still permits control-plane ↔ node communication on 443/10250.

#5.7 nginx Helm Release Capture — blocking gate (R-14, R-15, R-16)

Critical

nginx is hand-managed and outside Argo CD. Everything that makes the 45 microservices recoverable — Git history, declarative manifests, automated reconciliation — does not exist for the single component that fronts all of them. Until the steps below are complete and committed to Git, an ingress failure during node rotation has no documented recovery path. Treat this section as the highest-priority pre-work in the plan.

Step 1 — Identify the release and its true chart version.

export NS=<nginx-ns>

# The CHART column gives the real chart version; APP VERSION gives the nginx build.
# Confirm which one "1.21.3" actually refers to — they are frequently confused.
helm list -n $NS -o yaml | tee baseline-helm-list.yaml

# Full history, including superseded revisions
helm history <release> -n $NS

Step 2 — Extract every piece of release state.

# User-supplied values only — this is what a future `helm upgrade -f` must reproduce
helm get values <release> -n $NS -o yaml          > nginx-values.yaml

# Fully computed values (user + chart defaults) — reference for comparison
helm get values <release> -n $NS -a -o yaml       > nginx-values-all.yaml

# The exact rendered manifest currently running
helm get manifest <release> -n $NS                > nginx-manifest.yaml

# Any hook/notes metadata
helm get all <release> -n $NS                     > nginx-release-all.txt

# Raw Helm release Secret — the only authoritative copy of release state
kubectl get secret -n $NS \
  -l owner=helm,name=<release> \
  -o yaml                                         > nginx-helm-release-secrets.yaml

Step 3 — Vendor the chart itself (R-15).

# Pull and keep the exact chart version. Do NOT assume the repo will still serve it later.
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm pull bitnami/nginx --version <CHART_VERSION> -d ./vendor/

# If the version is already gone from the index, recover it from the release Secret:
#   the gzipped chart is embedded in sh.helm.release.v1.<release>.v<N>
kubectl get secret -n $NS sh.helm.release.v1.<release>.v<N> \
  -o jsonpath='{.data.release}' | base64 -d | base64 -d | gunzip > release.json
Tip

The Helm release Secret embeds the entire chart, double-base64'd then gzipped. If the upstream repo has already dropped your version, this is your recovery route — and it only works while the cluster and that Secret still exist. Extract it now, not during an incident.

Step 4 — Prove the image is still pullable (R-04).

kubectl get deploy -n $NS <nginx-deploy> \
  -o jsonpath='{.spec.template.spec.containers[*].image}'

# Prove it resolves from a clean cache TODAY
crane manifest <resolved-image-ref>     # or: docker pull --platform linux/amd64 <ref>

Step 5 — Commit everything to Git (platform/ingress/nginx/): nginx-values.yaml, nginx-manifest.yaml, the vendored chart .tgz, and a README recording the exact helm upgrade command, including the release name, namespace and -f file.

If the image pull or chart pull fails:

  1. Stop. Do not schedule the upgrade window.
  2. Mirror the image (by digest, not tag) to a private ECR repo in us-east-2; vendor the chart .tgz from the release Secret.
  3. Apply via a recorded values file as a separate, prior change:
    helm upgrade <release> ./vendor/nginx-<ver>.tgz -n $NS \
     -f nginx-values.yaml --set image.registry=<acct>.dkr.ecr.us-east-2.amazonaws.com
  4. Validate by deliberately deleting one nginx pod and confirming it re-pulls and reaches Ready.
  5. Confirm the NLB DNS name is unchanged after that change (§5.6).
  6. Only then schedule the upgrade.
Warning

--reuse-values vs --reset-values (R-16). Re-running helm upgrade without reproducing the original values is the most common way hand-managed releases get silently reset to chart defaults — which here would recreate the Service, mint a new NLB, and break the CloudFront origin. Always pass an explicit -f nginx-values.yaml. Never use ad-hoc --set flags that aren't recorded in that file.

This remains the single most likely cause of a non-recoverable ingress outage in this upgrade, because the failure only manifests at node-replacement time — long after the control plane has become unrollbackable.

#6.1 Backup Strategy

Although Git is the source of truth for the 45 microservices, back up what Git does not contain:

# Full cluster state snapshot
kubectl get all,cm,secret,ing,pdb,hpa,sa,pvc,crd -A -o yaml > full-cluster-backup.yaml

# Helm release state for ALL hand-managed releases (nginx especially) — see §5.7
helm list -A -o yaml > helm-releases-all.yaml
kubectl get secret -A -l owner=helm -o yaml > helm-release-secrets-backup.yaml

# Velero — namespaced resources + PV snapshots
velero backup create pre-upgrade-134 --include-cluster-resources=true --wait
velero backup describe pre-upgrade-134 --details
Warning

Secrets created out-of-band, controller-generated state (e.g. cert-manager-issued certs), any kubectl-applied drift, and the entire nginx Helm release exist only in the cluster. Velero plus the §5.7 capture are the only recovery paths for these.

#7. Phase 3 — Rehearsal (T−7 days, strongly recommended)

Because the control plane cannot be rolled back, rehearse on a disposable clone before touching kwg-nonprod:

  1. Provision kwg-upgrade-rehearsal at 1.34 using the same IaC module, same add-on versions, same VPC/subnet topology.
  2. Deploy a representative subset (nginx + ~5 microservices + scraper + log forwarder) via Argo CD.
  3. Execute the full Section 8 runbook end-to-end, timing each step.
  4. Record actual durations → calibrate the change-window estimate.
  5. Deliberately inject the top failure modes and practise the response:
    • A PDB with disruptionsAllowed=0 → observe PodEvictionFailure, practise remediation.
    • Delete the nginx image from the registry → observe ImagePullBackOff, practise ECR failover.
  6. Destroy the rehearsal cluster.

Output: a validated, timed runbook and a rehearsed team. If rehearsal is skipped (budget/time), R-01 and R-04 ratings should be escalated and explicitly accepted by the change approver.

Execute Hop 1 (1.34 → 1.35) completely, including the soak period, before beginning Hop 2 (1.35 → 1.36). Do not chain hops in a single window. Each hop is an independent change with its own go/no-go.

#Step 2 — Control Plane Upgrade (~25–45 min, AWS-managed)

export TARGET=1.35   # Hop 2: 1.36

aws eks update-cluster-version \
    --name $CLUSTER --region $REGION \
    --kubernetes-version $TARGET

# Capture the update ID and poll
UPDATE_ID=$(aws eks list-updates --name $CLUSTER --region $REGION \
            --query 'updateIds[0]' --output text)

watch -n 30 "aws eks describe-update --name $CLUSTER --update-id $UPDATE_ID \
             --region $REGION --query 'update.{Status:status,Type:type,Errors:errors}'"
Critical

Point of no return. Once this call is accepted, the cluster cannot be downgraded.

During the upgrade — expected behaviour:

  • Workloads continue running uninterrupted. Nodes are untouched.
  • Brief API-server unavailability / throttling is normal. kubectl may transiently error.
  • Argo CD may log connection errors — expected and harmless while frozen.
  • Synthetic monitor must stay green throughout. If it goes red, the problem is not the control-plane upgrade — investigate the data plane.

Validation:

aws eks describe-cluster --name $CLUSTER --region $REGION --query 'cluster.{v:version,s:status}'
kubectl version
kubectl get --raw /readyz?verbose
kubectl get nodes        # nodes still on old kubelet — expected and supported
Note

Version skew: a kubelet up to 3 minor versions older than the API server is supported, so 1.34 nodes under a 1.36 control plane are valid. This is what makes the two-hop control-plane-first sequence safe — but do not leave nodes behind permanently; finish the data plane in the same window.

Checkpoint: cluster ACTIVE at target version, /readyz ok, synthetic green.

#Step 4 — Data Plane: Bottlerocket Managed Node Groups (longest step — ~10–20 min per node)

This is where user impact occurs. Rotate one node group at a time, and within a group let EKS roll one node at a time.

4.1 — Set a conservative update config (per node group):

aws eks update-nodegroup-config \
    --cluster-name $CLUSTER --nodegroup-name <NG> --region $REGION \
    --update-config maxUnavailable=1

4.2 — Upgrade the node group. Because the AMI type is BOTTLEROCKET_x86_64 and (assuming) no custom launch template pins an AMI ID, EKS resolves the correct Bottlerocket AMI automatically:

aws eks update-nodegroup-version \
    --cluster-name $CLUSTER --nodegroup-name <NG> --region $REGION \
    --kubernetes-version $TARGET

If a custom launch template pins a specific AMI ID, --kubernetes-version is not sufficient. Resolve the new Bottlerocket AMI, create a new launch-template version, then upgrade:

aws ssm get-parameter --region $REGION \
  --name /aws/service/bottlerocket/aws-k8s-$TARGET/x86_64/latest/image_id \
  --query Parameter.Value --output text

Then: aws eks update-nodegroup-version --launch-template version=<N>,id=<lt-id> ...

4.3 — Monitor the rotation. The managed update proceeds in phases: setup → scale up (surge) → cordon & drain → scale down.

# In one terminal — node churn
watch -n 15 'kubectl get nodes -o custom-columns=\
NAME:.metadata.name,VER:.status.nodeInfo.kubeletVersion,\
STATUS:.status.conditions[-1].type,AGE:.metadata.creationTimestamp'

# In another — pods that failed to reschedule
watch -n 15 'kubectl get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded'

# In another — NLB target health (the real user-impact signal)
watch -n 20 "aws elbv2 describe-target-health --region $REGION \
  --target-group-arn <TG_ARN> \
  --query 'TargetHealthDescriptions[].TargetHealth.State' --output text"

# And the synthetic monitor must remain green

4.4 — Failure handling:

Symptom Diagnosis Action
Update status Failed, reason PodEvictionFailure A PDB is blocking drain (R-05) Identify via kubectl get pdb -A → disruptionsAllowed=0. Fix the PDB in Git, re-sync, retry. Only use --force-update-version with explicit approval — it evicts regardless of PDBs.
Pods Pending / FailedScheduling Insufficient capacity or AZ-pinned PVC (R-06/R-12) Check kubectl describe pod. Add capacity in the correct AZ.
nginx ImagePullBackOff R-04 materialised Immediately repoint to the ECR mirror. This is an ingress-down event.
InsufficientFreeAddresses Subnet IP exhaustion Free IPs / enable prefix delegation, retry.
Node NotReady after join CNI or add-on mismatch Check aws-node logs. Bottlerocket: use SSM + admin container (no SSH).
Tip

Bottlerocket debugging: there is no SSH and no shell on the host. Use aws ssm start-session --target <instance-id> then enter-admin-container, and apiclient get / journalctl -u kubelet from there.

4.5 — Repeat for every node group, validating between each.

Checkpoint: all nodes report the target kubeletVersion, zero NotReady, zero Pending pods, all NLB targets healthy, synthetic green.

#9.5 Soak Period

Soak for a minimum of 24 hours (48h preferred) after Hop 1 before starting Hop 2. Monitor:

  • Error rates / 5xx at CloudFront and nginx
  • Pod restart counts
  • HPA scaling behaviour over a full daily traffic cycle
  • Node stability (no unexpected NotReady, no OOM)
  • Nightly/batch jobs and CronJobs completing successfully

CronJobs are a common blind spot — a job that only runs at 02:00 will not be validated by a same-day soak. Confirm at least one full cycle of every scheduled workload before declaring the hop successful.

#10. Rollback & Contingency

#10.1 Rollback Capability by Layer

Layer Rollback possible? Method
Control plane No EKS does not support version downgrade. Roll forward or rebuild.
Managed node group Yes Re-run update-nodegroup-version targeting the previous AMI release version (valid while within the 3-minor kubelet skew).
EKS add-ons Yes update-addon to the prior --addon-version.
Workloads / Helm Yes 45 microservices: Git revert → Argo CD sync (argocd app rollback). nginx: helm rollback <release> <rev> -n $NS — manual, and only as good as the release history retained in-cluster.
Persistent data Yes Velero restore / EBS snapshot restore.

#10.2 Decision Tree

Failure during Step 2 (control plane)?
  └─ AWS rolls back automatically on failure; cluster stays at prior version.
     → Investigate `describe-update` errors. Re-attempt after remediation.

Failure AFTER control plane succeeded?
  ├─ Node group rotation failing?
  │     → Roll node group back to prior AMI release version. Cluster runs
  │       new control plane + old nodes (valid skew). Remediate, retry.
  ├─ Workload broken (deprecated API / incompatible controller)?
  │     → Fix forward in Git. Argo CD sync. This is the normal path.
  ├─ Add-on broken?
  │     → update-addon to prior version. Remediate, retry.
  └─ Ingress down (NLB changed / ImagePullBackOff)?
        → SEV-1. See 10.4.

#10.3 Catastrophic Contingency (control plane healthy but cluster unusable)

Last-resort path — expensive, slow (hours), and should never be needed in non-prod, but must be documented because R-01 has no in-place remedy:

  1. Provision a new EKS cluster at the last-known-good version via IaC.
  2. Register it with Argo CD; sync all 45 apps from Git.
  3. Velero-restore cluster-only state (secrets, PVs).
  4. Validate the new NLB provisioned by the nginx release.
  5. Update the CloudFront origin to the new NLB DNS name; wait for distribution deployment.
  6. Validate end-to-end, then decommission the broken cluster.

Step 5 is the long pole — CloudFront distribution updates take time to propagate. Factor this into any RTO commitment.

#10.4 Ingress-Down Emergency (R-03 / R-04 / R-14)

Warning

nginx is not reconciled by Argo CD. Nothing will fix it automatically — every step below is manual, and depends entirely on the §5.7 artifacts having been captured beforehand.

  1. Confirm scope: is the NLB DNS changed, or are nginx pods failing to start?
  2. If NLB DNS changed: update the CloudFront origin to the current NLB DNS immediately — this restores service fastest. Then investigate why the Service was recreated and restore the original.
  3. If ImagePullBackOff: patch the Deployment directly to the pre-mirrored ECR image reference for immediate relief:
    kubectl set image deploy/<nginx-deploy> -n $NS \
  nginx=<acct>.dkr.ecr.us-east-2.amazonaws.com/nginx@sha256:<digest>
    Then reconcile the Helm release to match, so the next helm upgrade does not revert it:
    helm upgrade <release> ./vendor/nginx-<ver>.tgz -n $NS -f nginx-values.yaml \
  --set image.registry=<acct>.dkr.ecr.us-east-2.amazonaws.com
  4. If the release itself is broken: helm rollback <release> <last-good-rev> -n $NS, then verify the NLB DNS is still unchanged.
  5. If the release is gone entirely: reinstall from the vendored chart + captured values — this is precisely the scenario §5.7 exists for:
    helm upgrade --install <release> ./vendor/nginx-<ver>.tgz -n $NS -f nginx-values.yaml
    Expect a new NLB; update the CloudFront origin accordingly.
  6. Do not continue the upgrade until ingress is green and stable.
Tip

A kubectl set image patch gives the fastest recovery, but Helm does not know about it. The next helm upgrade will silently revert to the broken image. Always follow step 3's patch with the matching Helm reconcile.

#13. Key Decisions Requiring Sign-Off

# Decision Recommendation
D-1 Two separate change windows (one per hop) vs a single combined window Two separate windows with a soak between. A combined window doubles the blast radius with no rollback, and makes attribution of any regression impossible.
D-2 Perform the rehearsal (Phase 3)? Yes. Given R-01 (no rollback), the cost of a disposable cluster is trivial against the cost of an unrecoverable non-prod cluster.
D-3 Mirror Bitnami nginx image to ECR Yes, unconditionally, as a prior change. Even if the pull works today, relying on a public registry for a tag this old is an unacceptable single point of failure during node replacement.
D-4 maxUnavailable for node rotation 1. Non-prod tempts you to go faster; resist it — the purpose of this run is to produce a trustworthy rehearsal of the production procedure.
D-5 Upgrade nginx chart from 1.21.3 to a current, supported release Yes — but as a separate change after the upgrade completes. nginx 1.21.x is long out of support. Never combine an ingress change with a cluster upgrade.
D-6 Migrate aws-auth ConfigMap → EKS Access Entries (if still on ConfigMap) Recommended, but after the upgrade as a separate change.
D-7 Onboard nginx into Argo CD (Helm-type Application or kustomize+helmCharts, pointing at the vendored chart and nginx-values.yaml) Yes — schedule immediately after the upgrade. Hand-managed ingress is the weakest link in this platform: highest blast radius, lowest recoverability, no drift detection, and a single person holding undocumented state. The §5.7 capture produces exactly the artifacts needed to onboard it. Do it after the upgrade so the two changes stay independent.
